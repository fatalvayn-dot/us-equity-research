# Development contract

Read docs/PROJECT_BRIEF.md and docs/DEVELOPMENT_STATUS.md before changes.
Inspect main, open PRs and Actions when GitHub is available. Use a feature
branch, execute unit/regression and relevant integration tests, create a PR,
and merge only verified changes. Do not commit secrets or cached provider data.
Do not use the legacy radar repository for new development.

Prioritize a concrete, tested improvement each session. Record failures, live
evidence, local-only results, commits/PRs, blockers and the next task in the
status file. Never count a fixture or unavailable adapter as live validation.
Preserve first-valid field priority and distinguish missing from unavailable.
No paid services, new permissions or real-money orders. Do not mark a later
stage complete while its prerequisite acceptance gate is unverified.

When repository creation is unavailable, preserve a Git bundle plus source
archive as a persistent checkpoint, and report the precise repository action
required. Avoid repeated identical notifications during scheduled attempts.
